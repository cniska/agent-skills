# Create

No formal verification skill exists yet: write `<project>-formal`.

1. **Pick the target by reading the code.** Start from an area or bug the user named. Otherwise read the code and ask only what it cannot show. Choose the guarantee whose failure would hurt users most and that no current test drives to its failing case, over the property easiest to check.
2. **Let the question pick the tool**, the cheapest one that answers it, and tell the user why. A question about steps landing in a harmful order goes to a model checker run on a compact abstraction of the design, TLA+ by default whatever the language. Whether the code holds for every input, such as memory safety, integer overflow or an invariant of a data structure, goes to a verifier that works on the source. Where the language has none, say so and fall back to property-based inputs driven through the actual functions. When no bound is enough and the claim must cover any size, reach for a proof assistant. Favor whatever the team can already set up on their own machines.
3. **Make it one of the repo's checks.** The check is one command under the repo's task runner, and once it is green, as step 6 says, the repo's check entry point calls it, so every change that runs the repo's checks runs it too. Pin the checker in the repo's own tool setup at a version that cannot move, its runtime included. Let the checker's non-zero exit on a violation fail the check.
4. **Write the model or harness to these rules:**
   - **Faithful.** Each variable, action and assumption traces to a file and symbol in the repo, named with this repo's nouns. Each action is one indivisible step in the code, and its name or its line in the coverage record gives that code's file and symbol.
   - **Able to fail**, as proven able to fail in `principles` says, shown for each property against a deliberately broken copy of the guarded code.
   - **Results stand.** A violation in today's code is a result to report, with the property and the model kept as written. Touch product code only at the user's request.
   - **Scoped honestly.** State a pass with its bounds and assumptions, and with what the model leaves out.
   - **Plain to read.** Say in plain words what must always hold, and separately what goes wrong for users if it does not. Tell a counterexample as a short sequence of plain steps in the code's own words, then replay it against the real code through a test written per `test-writing`. A step the code cannot take means the model is wrong. A chart of the model's states or of a counterexample's steps follows `docs-writing`.
   - **Cheap.** Keep the bounds small enough that the check takes no longer than the repo's slowest existing check.
   - **Tracked.** A coverage record names, per check, the files and functions it models, beside the sync commit: the newest commit whose code the model was checked against and found to match.
5. **Write the skill** in the shape of the repo's own skills. Its frontmatter names the area and when to load it, since an agent finds a skill only by its frontmatter. Reading only the skill, the next agent can see whether its change reaches covered code, run the check, separate a defect in the code from a defect in the model, and revise the model when the change alters behavior on purpose. The skill carries the coverage record and sync commit, and lets the sync commit advance only after the model is confirmed against the code at that later commit. Every command and path in it is the one this repo uses, all filled in.
6. **Prove it.** Walk the new skill end to end the way its reader would, against real code broken so it violates the property, the break made inside a temporary worktree so the working tree stays as it was. The check has to go red. Back in the working tree it is green, or red only for findings the report names. A check red on today's code is the result: the bug, told in plain steps with its replay test. The model, the skill and the replay test stay on the topic branch. The check joins the entry point only once it is green, in a commit on that branch, and the user decides whether a product fix lands first. Record the check's wall-clock time from this run in the skill. When a break goes undetected or a step will not run, fix the skill or the model and keep the break. A skill that never finished this run stays uncommitted.
