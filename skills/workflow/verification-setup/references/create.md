# Create

No verification skill exists yet: write `<project>-verify`, or `<project>-verify-<area>` for an area of a monorepo.

1. **Interview the repo.** Answer from code, and ask the user only what cannot be observed.
   - **Surface:** what a user touches, and the action and visible result that matter. Pick the primary surface and list the rest. Give surfaces separate recipes when their launch or controls differ.
   - **Run:** the repo's own run task, its ports, env vars, seed data and auth. When sign-in needs a human, find a test or guest login in tracked config or fixtures and enable it in gitignored local config. With none, report it as the blocker. Keep values from a deployed environment out of the skill.
   - **Drive:** reuse an existing agent-control recipe or harness, such as browser specs, PTY helpers, simulator tooling or a debug port, before adding one. The path drives the interface itself, beyond what a test suite covers.
   - **Observe:** the visible result, persistent side effects, and the diagnostics an engineer checks on this surface, such as console and page errors, failed requests, and server or daemon logs.
   - **Real machine:** whether a drive needs the developer's own home, credentials or account. When it does, bracket every such drive and every one-off command run while interviewing: fingerprint that state by metadata before and after, and fail on any change. Call a path read-only only once a bracketed run has shown it.
   - **Isolate:** walk the source for fixed ports, shared data directories, lock files and global state. When two instances cannot run side by side, the skill says so and drives only an instance it started.

   When `HEAD` does not build or start, stop and report it, since a skill written against a broken base teaches wrong steps. When the base is sound but this host lacks something, such as credentials or a toolchain, write the skill, leave it uncommitted, and report blocked with the step that unblocks the proving run.
2. **Write the skill**, laid out like the repo's other skills, with a `description` naming the app, the surface, and when to reach for it. Fill every step from the interview:
   - **Launch:** the exact command, readiness check and teardown. Derive ports, browser profiles and app data per run, so concurrent agents do not collide. Run the base build, the default branch or `HEAD` when the only change is this skill, from a second checkout with its own data, dependencies and generated files, driven by the current harness, since the harness may be newer than the base.
   - **Doctor:** one read-only check that the instance is worth driving: process up, the right build, and what this run owns on this surface, such as a port, a socket, a session or valid auth. Add the helpers' self-test. Every check can fail. Drop a check that does not apply, and drop one that compares a value with itself, since it proves nothing. Run Doctor first and whenever anything looks off.
   - **Drive:** this repo's real selectors, commands and routes. Prefer stable handles, such as accessibility labels, data attributes, prompt strings and routes, to coordinates and tab order.
   - **Evidence:** a per-run directory outside the checkout that cleanup keeps, named in the skill. Mask anything that can carry a credential, such as logs, DOM dumps and request captures, before writing it. Drive the path a user takes, through the controls a user has. Capture the action and the resulting state, and check side effects alongside what is visible. Mock only at a boundary production already isolates. Confirm by observation what a dry-run mode skips. For an interface, capture each visible state its feature file lists as an image and its frame dump, the accessibility tree with each element's frame, in every shipped theme, at every target size and the largest text size. Beside each, capture the reference screen it is judged against, the one the screen's platform reference in `ui-design` names, in the same theme and size, wherever the run can reach it, and say which it could not reach. For a terminal interface, each capture is the output text, escape codes kept, and the exit code, at each width the platform reference names, in place of an image, a frame dump and a text size.
   - **Findings:** where a defect in the change, a defect outside it, and a problem only this machine causes each get written down.
   - **Cleanup:** stop what the run started by PID or recorded identifier, so it stops only what this run started.
   - **Helpers:** script launch, readiness, evidence capture and cleanup so they fail loudly, and keep prose for what to operate and how to judge the result. Write helpers in the repo's own language on a harness it already has. With none, add the lightest one that ecosystem offers, its dependencies kept in the skill's directory. Show each invocation in the skill, and give the helpers one self-test of their contract (masking, exit status, timeouts), seen failing against a broken copy.
3. **Seed the feature map**: `features/README.md` indexing one file per user-facing feature, starting from the top few found in routes, commands, menus or docs. Each file has `Sub-features`, for an interface its `Visible states` with the reference screen each is judged against and how to reach it, `How to get to it (user POV)`, `Driving it with <harness>`, and `Gotchas`, and ends in the observable state that proves the feature works. Where the project has a spec with requirement IDs, each section cites the IDs wherever it would state behavior the spec states, the sub-features and the route to a screen included, and holds only what the spec does not, such as the commands, handles and gotchas a driver needs, since a restated line drifts when the spec changes. A proof drives every entry point the map lists.
4. **Prove it.** From a clean build, follow the skill through cleanup: Launch, Doctor, drive one mapped feature on both base and changed build, capture evidence, Cleanup. Run both builds at once to prove they do not collide, make one check fail to prove the run exits non-zero, and check a stored result when the behavior writes one. Confirm the evidence survives cleanup and no process or port is left. When controls are unreliable, improve the interface's semantic handles or add a driver. Run Cleanup after every failed attempt. Commit the skill only once it has completed this run.
