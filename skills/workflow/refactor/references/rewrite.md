# Rewrite

The design is wrong across modules whose patterns interlock. Each step holds on top of the skill's own rules.

1. **Requirements first.** Settle the spec with the owner before any design. The spec says what holds, in its own terms, apart from how the old code did it.
2. **Acceptance tests from the requirements.** Write each criterion as a test that drives only the public surface, such as the CLI, the API or the UI, and imports no internal module. Confirm each one fails.
3. **Delete the old code before designing.** On the rewrite's branch, remove the modules the requirements define anew, the files only they use, their tests, and the docs that describe how they work, a design written for the old code included. A shared file that kept code also uses stays. In each kept file, cut the import and the capability that needed it and keep the file, so the branch still passes its gate. The rewrite brings each capability back. Learn how a hard piece works from its external contract, such as the tool's documentation or the protocol, and leave the deleted code unread, since old code in reach pulls the new design toward it. Keep what outlives the code: stored data, applied migrations and a contract another deployed app calls. The new design reads them as they are and changes them through `deprecation`, unless the owner has declared that data disposable, in which case the new design owns its shape.
4. **Design from the requirements and the patterns.** Write the design document from the spec and `design-review`'s rules. Have `second-opinion` challenge it, and have the owner approve it before anyone writes code.
5. **Build what the spec requires.** List for the owner each old behavior the spec does not require, instead of rebuilding it. A capability the old system deferred stays deferred unless the spec asks for it, which keeps the second system from growing past the first.
6. **Build to the tests, part by part,** refactoring as you go by the skill's Refactor steps, with `design-review` on each finished part.
7. **Land in one change.** Once the replacement passes its acceptance tests, it lands with the old code gone, so each commit on the default branch runs one design.
